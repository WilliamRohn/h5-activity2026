# Canvas 拼图在高倍率缩放下的清晰度问题

> 本文归档的是重构前 `100 × 100`、`1200 × 1200` 固定 Canvas 实现，用于保留问题链路与决策背景，不代表当前配置。当前 `100 × 200` 视口级 Canvas 的实现与实测结果见 `docs/puzzle-performance-20000.md`。

## 1. 问题结论

当前拼图素材 `public/images/jiaoxu.svg` 是由矢量路径组成的 SVG，没有嵌入 PNG、JPEG 等位图资源。素材本身具备矢量图的缩放能力，但只有在浏览器继续通过 SVG 渲染管线绘制时，才能在放大后保持清晰。

现有实现会先把 SVG 绘制到固定分辨率的 Canvas。图片一旦进入 Canvas，就已经变成固定像素数量的位图；后续对 Canvas 元素做 CSS 放大，只会放大这些既有像素，不会重新计算 SVG 路径。因此，500% 缩放下的模糊不是 SVG 素材精度不足，而是渲染架构导致的栅格放大。

## 2. 当前实际渲染链路

```text
SVG 矢量图
  ↓ drawImage()
1200 × 1200 Canvas 位图
  ↓ CSS transform: scale(...)
最高放大至 500%
  ↓ 浏览器/GPU 插值
屏幕显示
```

相关实现位置：

- `src/config/puzzle.js`（归档时）：配置为 `100 × 100` 块、Canvas 分辨率 `1200`、缩放范围 `1–5` 倍。
- `src/components/PuzzleCanvas.jsx`：将 Canvas backing store 固定为 `resolution × resolution`，并通过 `drawImage()` 栅格化 SVG。
- `src/components/PuzzleViewport.jsx`：通过 CSS `translate3d(...) scale(...)` 对整个拼图舞台执行平移和缩放。
- `src/styles/app.css`：通过 CSS 渐变绘制网格，并为拼图舞台设置 `will-change: transform`。

## 3. 主要原因

### 3.1 Canvas backing store 分辨率固定

当前 Canvas 始终为 `1200 × 1200`，不会随着缩放倍率和设备像素比动态提高分辨率。

在 `100 × 100` 的拼图配置下，每一块拼图在 Canvas 中平均只有：

```text
1200 / 100 = 12 像素
```

即每块约为 `12 × 12` 个 Canvas 像素。500% 放大后，浏览器只能把这 12 个像素插值成更大的显示区域，无法补充矢量路径原有的细节。

### 3.2 CSS 放大不会重新渲染 SVG

现有缩放作用在已经绘制完成的 `.puzzle-stage` 上。CSS transform 改变的是最终合成层的显示尺寸，不会再次调用 Canvas 绘制逻辑，也不会要求 SVG 按新的倍率重新栅格化。

因此，尽管输入素材是 SVG，缩放阶段处理的对象实际已经是 Canvas 位图。

### 3.3 高质量平滑只能改善插值，不能增加细节

当前设置了：

```js
context.imageSmoothingEnabled = true
context.imageSmoothingQuality = 'high'
```

这些设置可以减轻锯齿，但本质仍是像素插值。它们不能恢复已经在首次栅格化时丢失的矢量信息，高倍率放大时还可能使边缘显得更柔和。

关闭平滑只会让画面变得像素化或产生明显锯齿，不属于真正的清晰度修复。

### 3.4 置灰滤镜和蒙层放大了模糊感

未点亮状态通过 Canvas `filter` 生成灰度、亮度和对比度效果，随后再覆盖一层低对比度半透明颜色。滤镜不是主要模糊来源，但置灰后的低对比度会降低边缘辨识度，让固定分辨率放大造成的柔化更加明显。

取消点亮时，只会把对应拼图块重新绘制到原有固定分辨率 Canvas 中，因此无法获得比基础 Canvas 更高的细节。

### 3.5 网格边框与整个舞台一起被缩放

拼图网格目前由 CSS `linear-gradient` 绘制，并位于被缩放的 `.puzzle-stage` 内。细线在基础倍率下可能落在半像素位置，进入 GPU 合成层后再放大，容易出现边缘发虚、粗细不均或颜色扩散。

`will-change: transform` 会鼓励浏览器提前为舞台创建合成纹理。它有利于手势动画性能，但也可能让浏览器持续缩放已经缓存的栅格图层。移除该属性可能改变部分浏览器的合成策略，但不能解决 Canvas 自身分辨率固定这一根本问题。

### 3.6 SVG 缺少 `viewBox` 不是当前问题的主因

当前 SVG 使用固定的 `width="628"` 和 `height="628"`，但没有声明 `viewBox`。后续可以补充 `viewBox="0 0 628 628"` 以完善素材的缩放语义和兼容性，但在现有 Canvas 固定分辨率架构下，单独增加 `viewBox` 仍然不会消除500%缩放模糊。

## 4. 分辨率与内存估算

若继续使用“整张拼图 Canvas + CSS 放大”的方式，为了在高 DPR 手机上覆盖500%缩放，理论分辨率需要接近：

```text
目标宽度 = 拼图视口 CSS 宽度 × 缩放倍率 × devicePixelRatio
```

以约 300 CSS px 宽的拼图视口、500% 缩放、DPR 3 为例：

```text
300 × 5 × 3 = 4500 像素
```

一个 `4500 × 4500` RGBA Canvas 的原始像素内存约为：

```text
4500 × 4500 × 4 ≈ 81 MB（约 77 MiB）
```

这还不包括浏览器内部纹理、滤镜缓冲、离屏合成和页面其他资源。移动端同时存在多个同尺寸缓冲区时，容易出现明显卡顿、Canvas 黑屏、纹理创建失败或页面被系统回收。因此，单纯把 `canvasResolution` 提升到 4500 或 5000 不适合作为长期方案。

## 5. 长期解决方案：基于视口的 Canvas 渲染

### 5.1 核心原则

将 Canvas 从“整张拼图的固定分辨率位图”改为“当前视口的实时渲染目标”：

- Canvas 的 CSS 尺寸等于拼图视口尺寸。
- backing store 尺寸设置为 `viewportSize × devicePixelRatio`。
- 平移和缩放参数直接应用到 Canvas 绘制矩阵，不再使用 CSS 放大 Canvas。
- 手势变化时通过 `requestAnimationFrame` 合并并重绘当前视口。
- SVG 每次根据当前可见范围和缩放倍率直接绘制到目标物理像素，因此500%下仍能利用矢量路径细节。

因为 Canvas 只覆盖屏幕中可见的视口，其内存消耗主要取决于视口尺寸和 DPR，而不再随最大缩放倍率成倍增长。

### 5.2 拼图状态蒙版

继续保留现有 `Uint8Array` 拼图状态，并增加一个逻辑尺寸为 `columns × rows` 的状态蒙版：

- `100 × 100` 配置下，蒙版仅需要 `100 × 100` 个状态像素。
- 一个蒙版像素对应一个拼图块。
- 点亮或取消点亮只更新对应的一个蒙版像素，状态更新保持 O(1)。
- 绘制蒙版时关闭图像平滑，使每个状态像素精确扩展到一个完整拼图块。

推荐合成流程：

1. 在可见 Canvas 中按当前视口变换绘制高清置灰 SVG。
2. 在视口尺寸的离屏缓冲区绘制同一位置的高清彩色 SVG。
3. 使用状态蒙版裁剪彩色层，只保留已点亮拼图块。
4. 将裁剪后的彩色层合成到置灰底图上。
5. 最后绘制网格和最近一次状态变化反馈。

离屏 Canvas 只是内部渲染缓冲区，不创建每块拼图对应的 DOM。页面仍保持一个可见 Canvas，DOM 数量不会随拼图数量增长。

### 5.3 清晰网格

不再把 CSS 渐变网格放在被缩放的舞台中，而是在视口 Canvas 上按当前变换计算可见行列线：

- 只绘制当前视口内可见的横线和竖线。
- 线条坐标对齐设备物理像素。
- 默认使用一设备像素线宽，避免半像素插值。
- 根据产品需要决定网格线保持固定屏幕宽度，或随缩放倍率有限增粗。

100 × 100 配置最多只有 101 条横线和 101 条竖线，绘制开销稳定，不需要创建网格 DOM。

### 5.4 保留现有业务接口

长期重构只替换渲染层，不改变现有业务语义：

- 保留 `pieceIndex`、`row`、`column`、`x`、`y` 等点击信息。
- 保留当前由视口坐标反算拼图坐标的命中逻辑。
- 保留点亮、取消点亮和随机领取共用同一份状态。
- 保留现有后端 API payload 和服务端结果优先原则。
- 保留 `1–5` 倍缩放范围、拖动和双指缩放手势。

### 5.5 长期方案优缺点

优点：

- SVG 在任意支持范围内按目标像素重新渲染，500%下保持清晰。
- Canvas 内存与视口大小相关，不与整张拼图的最大显示尺寸绑定。
- 网格可以精确对齐物理像素。
- 继续支持10,000块拼图，且 DOM 数量恒定。
- 点击命中、状态管理和后端协议可以保持兼容。

代价：

- 需要重构当前 Canvas 绘制和手势渲染链路。
- 需要处理 DPR、视口尺寸变化、绘制调度和离屏合成。
- 需要在低端移动设备上验证 SVG 重绘、Canvas filter 和蒙版合成性能。

## 6. 短期止血方案：动态提高整图 Canvas 分辨率

如果暂时不能实施视口渲染，可以保留现有 CSS transform 结构，在缩放结束后动态提升整张 Canvas 的 backing store 分辨率。

建议流程：

1. 根据 `viewportSize × scale × devicePixelRatio` 计算目标分辨率。
2. 手势进行中继续使用当前 Canvas 做 CSS transform，保证跟手性。
3. 手势结束或缩放停止一段时间后，按目标分辨率重新栅格化 SVG。
4. 扫描 `pieceStates`，恢复所有点亮和置灰状态。
5. 替换清晰版本后继续执行增量状态绘制。

必须增加安全限制：

- 设置最大 Canvas 边长，例如按浏览器能力限制在 4096 或更低。
- 设置总像素预算，而不是只限制单边长度。
- 将 DPR 限制在合理范围，低内存设备可以主动降级。
- 捕获 Canvas 创建或绘制失败，失败时继续保留旧画面。
- 缩放过程中不频繁调整 backing store，避免重复分配大块内存。

短期方案的优点是对现有代码侵入较小，能够明显改善中高倍率清晰度；缺点是高倍率和高 DPR 下内存成本很高，受不同移动浏览器的 Canvas 尺寸及纹理限制影响，无法保证所有设备在500%时都达到原生物理像素精度。

因此，该方案只作为过渡和降级策略，不作为最终渲染架构。

## 7. 方案对比

| 方案 | 清晰度 | 内存 | 手势性能 | 改造成本 | 定位 |
| --- | --- | --- | --- | --- | --- |
| 仅关闭 image smoothing | 边缘更硬但像素化 | 低 | 高 | 低 | 不推荐 |
| 直接提高固定分辨率 | 有限改善 | 高 | 中到低 | 低 | 临时验证 |
| 动态整图分辨率 | 中到高，受上限限制 | 高且波动 | 中 | 中 | 短期止血 |
| 视口 Canvas + 状态蒙版 | 高 | 稳定 | 高，可控 | 高 | 长期推荐 |

## 8. 后续验收标准

实施长期方案后至少验证：

- 在 100%、150% 和 500% 缩放下，彩色与置灰区域边缘均保持清晰。
- 网格在缩放和平移后无明显发虚、抖动、粗细不均和错位。
- 在 DPR 1、2、3 的设备或模拟环境中检查实际物理像素渲染。
- 在 320px、375px、430px 页面宽度下验证 Canvas 尺寸和坐标映射。
- 轻点、拖动、双指缩放、滚轮缩放和按钮缩放行为保持一致。
- 放大和平移后点击仍能准确获取 `pieceIndex`、行列及业务坐标。
- 点亮与取消点亮继续保持 O(1) 状态更新，后端请求参数不变。
- 10,000 块配置下不创建拼图块 DOM，页面 DOM 数量保持恒定。
- 连续缩放和平移时无明显掉帧、Canvas 黑屏或内存持续增长。
- `prefers-reduced-motion` 下关闭或降级非必要状态动画。

## 9. 最终建议

短期可使用“缩放结束后按像素预算动态重绘整图 Canvas”缓解模糊，但应明确分辨率和内存上限。

长期应采用“视口分辨率 Canvas + SVG 按当前变换重绘 + 拼图状态蒙版 + 视口网格”的架构。该方案能够同时满足 SVG 高清缩放、10,000 块拼图、移动端手势性能、单 Canvas DOM 和现有后端坐标协议等要求。
